# 0040: x86_64 Linux apps through box64, built in the VM

Status: accepted, built (`x86-apps`, 3.0.1); the feature `x86-apps`, off by
default, every route.

## Context

Omarchy in OmacVM is ARM64 Linux. Some Linux apps ship only for x86_64
(AppImages, tarballs, vendor CLIs). Apple's Rosetta reaches a Linux VM
only through Parallels or Apple Virtualization (UTM's other backend).
OmacVM.app (QEMU), OmacVM's UTM VMs (QEMU) and VMware Fusion have no
Rosetta. So the VM needs its own x86_64 translator, the same on every
route.

Options:

- **FEX-Emu**: very compatible, but no release binaries (an Ubuntu PPA only),
  a clang/LLVM build, and an x86_64 root file system image (about 1 GB) for
  the libraries. Too heavy for an opt-in that should take minutes.
- **box64**: one program. It translates the app's own code and replaces
  common libraries (glibc, GTK, X11, Wayland, OpenGL, SDL, FUSE and more)
  with the VM's native ones, so most apps need no x86 root file system.
  Upstream ships a 34 MB bundle of the other x86_64 libraries.
- **qemu-user** (in Arch Linux ARM): emulates everything, libraries
  included, and needs an x86_64 root file system. Slowest.

Neither box64 nor FEX is in Arch Linux ARM's repositories (checked
2026-10-06).

## Decision

box64, pinned to a commit with its sha256 (main from 2026-09-30, 347
commits after 0.4.4: in 0.4.4 threaded x86_64 programs such as Node.js
print their result and never exit) and the x86_64 part of upstream's 0.4.4
library bundle, built in the VM as a pacman package
(`src/x86/guest/PKGBUILD`, like the vulkan feature's Mesa). Generic ARM64
build, not upstream's M1 profile (that one is for Asahi's 16 KiB pages).
Its binfmt rule goes to `/usr/lib/binfmt.d`, so x86_64 programs and
AppImages start like native ones. Off by default, tagged experimental and
slow.

## Consequences

- One `pacman -R omacvm-box64` removes everything; `omacvm disable
  x86-apps` does that (only for OmacVM's own package; a box64 installed by
  hand stays). The package is not called `box64`: the AUR has a box64, and
  Omarchy's update (`yay -Sua`) would replace ours with it once its version
  is higher (no malloc hack, no library bundle, and no longer OmacVM's to
  remove). It provides and conflicts with `box64`.
- Turning it on takes about 2 minutes on an M4 (the build) and about 70 MB of downloads.
- x86_64 apps run slower than native ARM ones; numbers in
  [../features.md](../features.md#x86-linux-apps). 32-bit x86 and Windows apps
  (Wine) are not part of it.
- box64's malloc hack is on for every program (a `[*]` entry in the
  package's `/etc/box64.box64rc`): Electron apps hang or crash without it,
  and box64 sets it only for apps it knows by name. 7-Zip, ripgrep and
  Node.js run as fast with it. box64 reads its rc files after the
  environment, so `BOX64_MALLOC_HACK=0` in the environment does not turn
  it off; an entry for the program in `~/.box64rc` does.
- On Parallels, Rosetta could be faster; wiring it up is not part of this
  (one translator everywhere is simpler to support).
- A newer box64 is a PKGBUILD change (commit or release, sha256) that the
  update shows on the feature's row. Back to a release once one has the
  exit fix.

## Amendment (3.4.2): who gets x86_64 programs

Omarchy 4.5 brings `qemu-user-static-binfmt`. Its rule
`/usr/lib/binfmt.d/qemu-x86_64-static.conf` has the same x86_64 magic as
box64's. systemd-binfmt (at boot, on a restart of the unit, and from
systemd's pacman hook) takes every rule out and loads the binfmt.d files in
file-name order, so qemu's comes after `box64.conf` and the kernel, which
tries the newest rule first, gives x86_64 programs to qemu-user. It has no
x86_64 glibc, so dynamic programs fail (#752).

- While x86 apps is on, `install.sh` writes
  `/etc/binfmt.d/qemu-x86_64-static.conf`, comments only, its first line
  OmacVM's. A file in `/etc/binfmt.d` hides the `/usr/lib` one of the same
  name, so qemu's x86_64 rule is not loaded any more; its other rules stay.
  It is written before `pacman -U`, whose hook loads the rules. A file of
  that name that is not OmacVM's (or a link) is left alone.
- Off removes the file only when it is OmacVM's, after `pacman -R` worked,
  then reloads once: qemu's rule is back at once and after a restart.
- `--status` is `broken` when any other enabled rule matches an x86_64 ELF
  (executable or PIE) under its mask, and names it. Only qemu-user's rule is
  held back; any other (FEX, the person's own) makes `on` fail with its name.
- Not chosen: renaming box64's rule to sort last (relies on name order, needs
  a box64 rebuild on every VM, qemu's rule stays live) or the mask inside
  the package (same rebuild, a file conflict with the person's own file).
  Removing qemu-user-static-binfmt would change Omarchy's package set.
- Existing VMs get it from the next apply or Update VM, no rebuild and no
  restart. An app downgraded to 3.4.1 keeps the file (3.4.1's off does not
  know it): qemu's x86_64 rule stays held back until a 3.4.2 or newer off.
- Also 3.4.2: off and the box64 upgrade path removed `box64` by name when
  `pacman -Q box64` answered, but that also answers with `omacvm-box64`
  (it provides box64), and `pacman -R box64` then stopped with "target not
  found" (#751). Only a package named box64 is OmacVM's old one now.

## Amendment (3.4.7): the build fits small VMs

box64's `src/tools/gtkclass.c` (macros that expand to thousands of
functions) took GCC 4.1 GB with `-g` (RelWithDebInfo), measured in a 3 GB
VM with a 4 GB swapfile so it could finish. A 3 GB VM with the desktop
open has about 1.9 GB free plus 738 MB zram (capped at a quarter since
3.4.2, #746), so the kernel killed the compiler (m1-1114: 3 of 3 failed).
The whole -j4 build peaks only about 70 MB above that file alone: the job
count is not the problem.

- `build()` takes makepkg's own flags (`CMAKE_BUILD_TYPE=None`: -O2, no -g,
  as the package is built with `!debug` and `strip --strip-debug` anyway)
  plus upstream's `-DNDEBUG`, and `--param ggc-min-expand=20 --param
  ggc-min-heapsize=32768`: GCC collects its garbage when the heap has grown
  by 20 % instead of doubling. The file then peaks at 1.24 GB (2.09 GB
  without the params, 4.1 GB as before) in 76 s; the object file is
  byte-identical with and without the params. The whole switch-on path in a
  3 GB / 4 CPU VM with the desktop open: 171 s, at least 833 MB free.
- pkgrel stays 1: the code is the same, so `--status` stays ok on VMs that
  have box64 and Update VM does not rebuild it.
- `install.sh on` checks MemAvailable + SwapFree before the build tools go
  in (after the ok and broken exits, so a VM that has box64 never runs it):
  under 1.5 GB it stops with one `OmacVM: ` line (the VM's free memory,
  rounded down to 0.1 GB). No `/proc/meminfo` or no MemAvailable: no check.
  A build that fails with gcc's `Killed signal terminated program` or a
  kernel `Out of memory: Killed process` line since the build started
  (`journalctl -k --since`) ends with an `OmacVM: ` line that names memory
  and the VM's size in whole GB (MemTotal rounded, so a 4096 MB VM says 4).
  `cmd/apply.sh` (`why_not`) shows the last `OmacVM: ` line of a switch as
  the reason. Nothing changes in the app or `features.tsv`: users cannot
  make a VM under 4 GB, and 4 GB fits with room.
- Not chosen: a prebuilt package (a release asset per box64 bump, an
  aarch64 build in the release, and one glibc for every VM), a temporary
  swapfile (btrfs needs its own subvolume and `mkswapfile`, up to 4 GB
  written to the Mac's SSD per build, and the desktop crawls at 7 MB free;
  the fallback if a later box64 outgrows this), a higher memory minimum for
  the feature, `-O1` for that file (1.94 GB, other code), fewer jobs (one
  job failed too). Upstream knows the file is heavy (ptitSeb/box64#3636).
