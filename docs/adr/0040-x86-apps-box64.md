# 0040: x86_64 Linux apps through box64, built in the VM

Status: accepted, built (`x86-apps`, 3.0.1); the feature `x86-apps`, off by
default, every route.

## Context

Omarchy in OmacVM is ARM64 Linux. Some Linux apps ship only for x86_64
(AppImages, tarballs, vendor CLIs). Apple's Rosetta reaches a Linux VM
only through Parallels or Apple Virtualization (UTM's other backend).
OmacVM.app (QEMU), OmacVM's UTM VMs (QEMU) and VMware Fusion have no
Rosetta. So the VM needs its own x86_64 translator, the same on every
route.

Options:

- **FEX-Emu**: very compatible, but no release binaries (an Ubuntu PPA only),
  a clang/LLVM build, and an x86_64 root file system image (about 1 GB) for
  the libraries. Too heavy for an opt-in that should take minutes.
- **box64**: one program. It translates the app's own code and replaces
  common libraries (glibc, GTK, X11, Wayland, OpenGL, SDL, FUSE and more)
  with the VM's native ones, so most apps need no x86 root file system.
  Upstream ships a 34 MB bundle of the other x86_64 libraries.
- **qemu-user** (in Arch Linux ARM): emulates everything, libraries
  included, and needs an x86_64 root file system. Slowest.

Neither box64 nor FEX is in Arch Linux ARM's repositories (checked
2026-10-06).

## Decision

box64, pinned to a commit with its sha256 (main from 2026-09-30, 347
commits after 0.4.4: in 0.4.4 threaded x86_64 programs such as Node.js
print their result and never exit) and the x86_64 part of upstream's 0.4.4
library bundle, built in the VM as a pacman package
(`src/x86/guest/PKGBUILD`, like the vulkan feature's Mesa). Generic ARM64
build, not upstream's M1 profile (that one is for Asahi's 16 KiB pages).
Its binfmt rule goes to `/usr/lib/binfmt.d`, so x86_64 programs and
AppImages start like native ones. Off by default, tagged experimental and
slow.

## Consequences

- One `pacman -R omacvm-box64` removes everything; `omacvm disable
  x86-apps` does that (only for OmacVM's own package; a box64 installed by
  hand stays). The package is not called `box64`: the AUR has a box64, and
  Omarchy's update (`yay -Sua`) would replace ours with it once its version
  is higher (no malloc hack, no library bundle, and no longer OmacVM's to
  remove). It provides and conflicts with `box64`.
- Turning it on takes about 2 minutes on an M4 (the build) and about 70 MB of downloads.
- x86_64 apps run slower than native ARM ones; numbers in
  [../features.md](../features.md#x86-linux-apps). 32-bit x86 and Windows apps
  (Wine) are not part of it.
- box64's malloc hack is on for every program (a `[*]` entry in the
  package's `/etc/box64.box64rc`): Electron apps hang or crash without it,
  and box64 sets it only for apps it knows by name. 7-Zip, ripgrep and
  Node.js run as fast with it. box64 reads its rc files after the
  environment, so `BOX64_MALLOC_HACK=0` in the environment does not turn
  it off; an entry for the program in `~/.box64rc` does.
- On Parallels, Rosetta could be faster; wiring it up is not part of this
  (one translator everywhere is simpler to support).
- A newer box64 is a PKGBUILD change (commit or release, sha256) that the
  update shows on the feature's row. Back to a release once one has the
  exit fix.
